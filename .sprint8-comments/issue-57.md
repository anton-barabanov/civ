## Дизайн-ревью (архитектор) — S8-2 Религия по торговым путям, волна 2 из 5 (после #56; → #58 → #59∥#60 → #61)

Решение владельца продукта: карта меняется в #58 — здесь НЕ привязываться к размерам (никаких литералов 26/18/468, писать через W/H). Порог распространения остаётся 5 (REL_SPREAD_THRESHOLD:157 не трогаем).

### Ключевые решения

1. **Морская связь — «уточнить» то, что есть** (spreadReligions:1037-1044): прибрежный город-приёмник + sailing у владельца приёмника + общий водный компонент (waterComp) с прибрежным городом-источником. Внимание: здания «гавань» в BUILDINGS (58-69) НЕ существует — требование тела issue «гавань у обоих» нереализуемо без нового контента; фиксируем текущее правило (sailing приёмника + общий waterComp) как итоговое. Отклонение от тела issue — документировано.
2. **Дорожная связь — НОВОЕ** (+1 к давлению): города связаны дорогой, если от соседей города-приёмника до соседей города-источника есть непрерывная цепочка `roadDoneAt`-клеток по passable-суше. Реюз механики landTradeActive (927-951), но БЕЗ гейта `tileOwner === c.owner` и БЕЗ гейта «свой город»: дороги любых владельцев, любой территории, источник — любой город с религией (не только свой). Дороги под городами не бывают (startImprovement:856), поэтому связь — через соседние клетки, как в landTradeActive.
3. **Реализация без шторма BFS**: в начале spreadReligions один раз за вызов построить компоненты дорожной сети: BFS/union-find по клеткам `roadDoneAt(k) && TERRAIN[map[k]].passable` (ребра — neighbors). Город «на сети», если хоть один его сосед в компоненте. Пара (приёмник, источник) связана ⇔ оба касаются одной компоненты. spreadReligions вызывается один раз за ход из processEconomy:1470 — кэш «на ход» выполняется тривиально (одно вычисление на вызов), отдельного кэширующего слоя НЕ вводим. Стоимость: один проход по ≤ W*H клеткам — дёшево даже на 864.
4. **Давление**: `pressure = near.length + tradeBonus`, где `tradeBonus = 1`, если есть морская ИЛИ дорожная связь с каким-либо городом религии (не входящим в near). **Не стакается**: дорога+море одновременно = всё равно +1 (один канал «торгового пути», решено так — простота и отсутствие двойного счёта с торговым золотом). Порог остаётся REL_SPREAD_THRESHOLD=5.
5. **Выбор источника** при срабатывании порога (1048-1049): кандидаты = near + sea + roadLinked; сортировка та же (по dist, затем по id — детерминированно). Приоритет госрелигии владельца пути и бонус святого города из тела issue — в спринт НЕ берём (упрощение, backlog), святыми городами источник становится как обычный кандидат.
6. **Лог**: если религия пришла и связь была торговой (источник дальше REL_SPREAD_RADIUS) — addLog «Религия X пришла в Y по торговому пути (дорога/море)».
7. **Экономику путей не трогаем**: tradeActive/landTradeActive/cityYields (торговое золото) — отдельная механика, давление религии её не изменяет; миссионеры/госрелигия работают как раньше.

### Тест-сценарии (headless; размеры через api.S.map.length / api.S.map, без литералов)
1. Сценарий двух цепочек: город A с религией, город B дальше REL_SPREAD_RADIUS от A, город C-контроль без дороги. Прокладываем дорогу A→B (S.impr[k] = {kind:"road"} по прямой) → relPressure B растёт на +1/ход (near вне радиуса даёт 0), у C — 0. К ходу ~5 B принимает религию, в логе «по торговому пути (дорога)».
2. Дорога + море одновременно: прибрежная пара с общим waterComp и дорогой → давление всё равно +1 (не стакается).
3. Море без sailing у приёмника → морского бонуса нет (регресс существующего поведения 1037).
4. Компонентность: разрыв дороги посередине (impr=null) → связь пропадает на следующем ходу.
5. Порог: давление копится до 5 и сбрасывается (relPressure=0 после принятия) — старые проверки порога зелёные.
6. Идемпотентность в рамках хода: повторный вызов spreadReligions до endTurn не даёт двойного давления (компоненты пересчитываются, давление — те же +1).
7. Регресс: радиус-3 и море без изменений (существующие проверки религии в run.mjs зелёные без правок ожиданий).
